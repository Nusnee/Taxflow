# TaxFlow — ระบบจัดการภาษีและเอกสารอิเล็กทรอนิกส์ (ระบบต้นแบบ)

## ใหม่ใน ver14 (โปรไฟล์แยกบทบาท + ยืนยันตัวตน + โลโก้บนเอกสาร + PDPA)

### 1) หน้าลงทะเบียนใหม่ แยกข้อมูลตามบทบาท

เขียนหน้า `login.html` ใหม่ทั้งหมดเป็นแบบ 3 ขั้นตอน (บทบาท → ข้อมูลผู้เสียภาษี → บัญชีและความยินยอม)

* **เอเจนซี่เลือกได้ว่าเป็นนิติบุคคลหรือบุคคลธรรมดา** ฟอร์มจะเปลี่ยนฟิลด์และเอกสารที่ต้องใช้ตามการเลือก
* เพิ่มฟิลด์ที่กฎหมายบังคับซึ่งเวอร์ชันก่อนไม่มี: **สำนักงานใหญ่/เลขที่สาขา** (ประมวลรัษฎากร มาตรา 86/4),
  ประเภทนิติบุคคล, กรรมการผู้มีอำนาจลงนาม, สถานะ VAT, ที่อยู่แบบแยกช่อง 6 ช่อง และบัญชีธนาคาร
* **ตรวจเลขประจำตัวผู้เสียภาษี 13 หลักด้วยสูตร check digit** ทั้งฝั่งหน้าเว็บและเซิร์ฟเวอร์ (`lib/thaiid.js`)
  พร้อมกันเลขซ้ำกับบัญชีอื่น

### 2) OTP ตอนสมัครสมาชิก (จุดที่ 3)

เดิมระบบยืนยัน OTP ตอนเข้าสู่ระบบและตอนลงนาม แต่**ไม่ได้ยืนยันตอนสมัคร** ทำให้สมัครด้วยอีเมลของคนอื่นได้
ver14 เพิ่ม `purpose: 'register'` — สมัครแล้วบัญชียังใช้งานไม่ได้จนกว่าจะยืนยันอีเมล
และถ้าล็อกอินด้วยบัญชีที่ยังไม่ยืนยัน ระบบจะส่งรหัสให้ใหม่อัตโนมัติ

**เรื่อง SMS**: ยังคงใช้อีเมลช่องทางเดียว เพราะ SMS ต้องเรียก API ภายนอก (ขัดข้อกำหนด zero-dependency),
มีค่าใช้จ่ายรายข้อความ, ต้องจดทะเบียนชื่อผู้ส่งในนามนิติบุคคล และต้องเก็บเบอร์โทรเพิ่มโดยไม่จำเป็นตาม PDPA
แต่ `lib/otp.js` ออกแบบให้มีฟิลด์ `channel` รองรับไว้แล้ว กรณีที่ SMS เหมาะกว่าอีเมลจริง ๆ มี 3 กรณี
คือ เปลี่ยนอีเมล/กู้คืนบัญชี, เปลี่ยนเลขบัญชีธนาคาร และลงนามเอกสารมูลค่าสูง (บันทึกไว้เป็นข้อเสนอแนะการพัฒนาต่อ)

### 3) โปรไฟล์แบบละเอียดตามบทบาท

หน้าโปรไฟล์เดิมมีแค่ 3 ช่อง เปลี่ยนเป็นหน้าเต็ม (`public/js/profile.js`) แบ่ง 6 กลุ่ม:
ข้อมูลผู้เสียภาษี · ที่อยู่และการติดต่อ · บัญชีธนาคาร · โลโก้และตราประทับ · เอกสารยืนยันตัวตน · ความเป็นส่วนตัว
ใช้ไฟล์เดียวร่วมกันทั้ง `creator.html` และ `agency.html`

* **แถบความครบถ้วน** แสดงเป็นเปอร์เซ็นต์พร้อมบอกว่าขาดอะไร
* **บังคับความครบถ้วนก่อนออกเอกสาร** — ถ้าข้อมูลไม่ครบตามที่มาตรา 86/4 กำหนด ระบบจะไม่ให้สร้างเอกสาร
* **ล็อกใบกำกับภาษีตามสถานะ VAT** — ผู้ที่ไม่ได้จดทะเบียน VAT ออกใบกำกับภาษีไม่ได้ตามมาตรา 86
  ระบบแนะนำให้ออกใบเสร็จรับเงิน/ใบแจ้งหนี้แทน
* แก้ข้อมูลสำคัญหลังผ่านการตรวจสอบแล้ว ระบบส่งกลับไปรอตรวจสอบใหม่อัตโนมัติ

### 4) เอกสารยืนยันตัวตน (KYC) + บทบาทผู้ดูแลระบบ

* ตารางใหม่ `kyc_documents` (ของเดิม `attachments` ผูกกับเอกสาร ใช้เก็บเอกสารระดับผู้ใช้ไม่ได้)
* เอกสารที่ขอแยกตามบทบาท: นิติบุคคลใช้หนังสือรับรอง + ภ.พ.20 (ถ้าจด VAT) + หน้าสมุดบัญชี /
  บุคคลธรรมดาใช้หน้าสมุดบัญชีอย่างเดียว
* **ไฟล์ถูกเข้ารหัส AES-256-GCM ก่อนเขียนลงดิสก์** (`lib/filestore.js`) — เดิมเก็บเป็นไฟล์เปล่า
  ใครเข้าถึงเครื่องได้ก็เปิดดูสำเนาบัญชีธนาคารได้ทันที
* **เพิ่มบทบาท `admin`** พร้อมหน้า `admin.html` สำหรับตรวจและอนุมัติ — เดิมให้อัปโหลดแล้วไม่มีใครตรวจ ระบบไม่ครบวงจร
  กรณีไม่อนุมัติต้องระบุเหตุผลเสมอ และสมัครเป็น admin ผ่านหน้าลงทะเบียนไม่ได้

### 5) โลโก้และตราประทับบนเอกสารที่ส่งออก

* อัปโหลดโลโก้ (≤ 1 MB) แล้วระบบพิมพ์ลงหัวกระดาษของ **เอกสาร PDF ทุกประเภท** และ **หัวรายงานในไฟล์ Excel**
* ตราประทับบริษัทแยกอีกรูป พิมพ์เหนือช่องลงนามของผู้ออกเอกสาร
* จำกัดความสูงโลโก้ตายตัวกันเลย์เอาต์พัง และวางไว้เหนือเนื้อหา **ไม่ทับรายการที่กฎหมายบังคับให้แสดง**
* ไฟล์ CSV ใส่รูปไม่ได้ จึงใส่ชื่อผู้ประกอบการ เลขผู้เสียภาษี ที่อยู่ และวันที่ออกรายงานเป็นบรรทัดหัวรายงานแทน
* เอกสาร PDF ยังได้ **สาขา** และ **ที่อยู่แบบเต็มรูปแบบราชการ** เพิ่มด้วย

### 6) การคุ้มครองข้อมูลส่วนบุคคล (PDPA)

* **ความยินยอมแบบแยกรายวัตถุประสงค์** 4 ข้อ (บังคับ 2 / เลือกได้ 2) ตามมาตรา 19 วรรคสาม
  ถอนข้อที่ไม่บังคับได้เองที่หน้าโปรไฟล์ ถอนแล้วอัปโหลดเอกสารยืนยันตัวตนไม่ได้ทันที
* **สิทธิขอสำเนาข้อมูล** (มาตรา 30) — ดาวน์โหลดข้อมูลทั้งหมดเป็น JSON
* **สิทธิขอลบ** (มาตรา 33) — ลบข้อมูลระบุตัวตน ไฟล์ และสมุดคู่ค้าทั้งหมด แต่คงเอกสารภาษีไว้แบบไม่ระบุตัวบุคคล
  เพราะประมวลรัษฎากร มาตรา 87/3 บังคับให้เก็บ 5 ปี (ข้อยกเว้นตามมาตรา 33 วรรคท้าย)
* **ลบข้อมูลที่หมดความจำเป็นอัตโนมัติ** — OTP ที่ใช้แล้วลบใน 24 ชม. แจ้งเตือนที่อ่านแล้วลบใน 90 วัน
  (เดิม `otp_codes` สะสมไปเรื่อย ๆ ไม่มีการล้าง)
* **บันทึกการเปิดดูเอกสารยืนยันตัวตนทุกครั้ง** ระบุว่าผู้ตรวจสอบหรือเจ้าของเป็นผู้เปิด
* **ไม่เก็บข้อมูลที่ไม่จำเป็น** — ไม่ขอสำเนาบัตรประชาชน (เก็บแค่เลข 13 หลัก เลี่ยงข้อมูลอ่อนไหวตามมาตรา 26),
  ไม่เก็บวันเกิด/เพศ/สถานภาพสมรส, ไม่เก็บข้อมูลช่องทางโซเชียลและสถิติผู้ติดตาม
  (ระบบทำหน้าที่จัดการเอกสารภาษีอย่างเดียว จึงไม่มีเหตุผลตามกฎหมายที่จะเก็บ),
  ไม่บันทึก IP ในบันทึกความยินยอม
* เพิ่มหน้า `privacy.html` อธิบายว่าเก็บอะไร เพราะอะไร นานเท่าไร และมีสิทธิอะไรบ้าง

### 7) เอกสารประกอบ

ปรับ `overview.html` (เพิ่มหัวข้อ PDPA และสิทธิ์ตามสถานะ VAT) และ `guide.html`
(เพิ่ม 4 หัวข้อใหม่: โปรไฟล์และการยืนยันตัวตน / โลโก้บนเอกสาร / PDPA / คู่มือผู้ดูแลระบบ)

### สิ่งที่ยังไม่ได้ทำ (ข้อเสนอแนะการพัฒนาต่อ)

* OTP ทาง SMS สำหรับธุรกรรมที่ควรแยกช่องทางจากอีเมล
* เชื่อมฐานข้อมูลกรมพัฒนาธุรกิจการค้าเพื่อตรวจหนังสือรับรองอัตโนมัติ
* แนะนำอัตราภาษีหัก ณ ที่จ่ายอัตโนมัติตามประเภทผู้รับเงินและประเภทงาน (2% / 3%)
* ย้ายทุกอย่างใน ver13–ver14 ไปยังเวอร์ชัน PostgreSQL

## ใหม่ใน ver13 (แก้บั๊กสมัครสมาชิก/เข้าสู่ระบบ + เพิ่ม OTP อีเมลจริง + ภาพรวมระบบ)

**1) แก้บั๊กหน้าเข้าสู่ระบบ/สมัครสมาชิก (ตามภาพหน้าจอที่พบ)**
สาเหตุจริง: `public/login.html` มี `</div>` เกินอยู่ 1 ตัวหลังตัวเลือกบทบาท ทำให้ HTML ซ้อนกันผิด — ช่องรหัสผ่านและปุ่ม "สร้างบัญชี" ของฟอร์มสมัครสมาชิกหลุดออกไปอยู่นอกกล่องที่ถูกซ่อนไว้ (`#register-view`) เลยโผล่ค้างอยู่ใต้ฟอร์มเข้าสู่ระบบตลอดเวลา (ตามภาพที่เห็น) นอกจากนี้ฟอร์มสมัครสมาชิกยังขาดช่องกรอกชื่อ/เลขผู้เสียภาษี/อีเมลไปเลย (JS อ้างถึง element ที่ไม่มีอยู่จริง) และตัวเลือกบทบาทใช้ class ที่ไม่มีอยู่ใน CSS เลยไม่มีสไตล์ใดๆ ทั้งหมดนี้แก้ไขและสร้างฟอร์มใหม่ทั้งหมดแล้ว รองรับสมัครสมาชิกครบทั้ง 3 บทบาท พร้อมช่องยืนยันรหัสผ่าน
ระหว่างแก้ ยังพบและแก้บั๊กเดิมอีกจุด: ตอน login/register สำเร็จ ระบบ redirect บทบาท "บริษัท (corporate)" ไปหน้า creator.html ผิด ทั้งที่ควรไปหน้า agency.html (หน้าเดียวกับเอเจนซี่) — แก้ให้ตรงกับตรรกะ `guard()` ที่ถูกต้องอยู่แล้วใน common.js

**2) ยืนยันตัวตนด้วยรหัส OTP ทางอีเมลจริง (Gmail)**
เพิ่มระบบส่ง OTP ด้วย SMTP ล้วน (`lib/mailer.js`) ผ่าน `node:tls` — **ไม่ใช้ไลบรารีภายนอกใดๆ** ยังคงหลักการ zero-dependency เดิม บังคับยืนยัน OTP 2 จุดตามที่กำหนด:
  - ทุกครั้งที่ **เข้าสู่ระบบ** (หลังกรอกอีเมล/รหัสผ่านถูกต้อง)
  - ทุกครั้งที่ **ลงลายมือชื่อดิจิทัล** ทั้งการเซ็นเอกสารของตัวเอง และเซ็นตอบกลับเอกสารที่คู่ค้าส่งมา

รหัส OTP: 6 หลัก, อายุ 5 นาที, ใช้ได้ครั้งเดียว, กรอกผิดได้ไม่เกิน 5 ครั้ง, ขอรหัสใหม่ได้ทุก 45 วินาที (`lib/otp.js`) — เก็บเฉพาะแฮชของรหัสในฐานข้อมูล ไม่เก็บรหัสจริง

**การตั้งค่าให้ส่งอีเมลจริง:** คัดลอก `data/mail.config.example.json` → `data/mail.config.json` แล้วกรอก Gmail + App Password (วิธีขอ App Password มีอธิบายในคอมเมนต์ของ `lib/mailer.js`) หากยังไม่ตั้งค่า ระบบจะเข้า **โหมดพัฒนา** อัตโนมัติ: แสดงรหัส OTP บนหน้าจอแทนการส่งอีเมลจริง เพื่อให้ทดสอบ/สาธิตต่อเนื่องได้โดยไม่ติดขัด

**3) ภาพรวมและโครงสร้างระบบใหม่**
เพิ่มหน้า `overview.html` อธิบายขอบเขตของระบบอย่างชัดเจน (ไม่เชื่อมต่อกรมสรรพากร/ETDA จริง, ลายเซ็นเป็นภาพจำลอง XAdES/PAdES, จุดที่ต้องใช้ OTP, ไม่ยื่นแบบอัตโนมัติ ฯลฯ), รายละเอียดความสามารถของทั้ง 3 บทบาท, และตารางเปรียบเทียบ "เอกสารที่ออกเองได้ตามกฎหมาย" กับ "เอกสารที่หน่วยงานรัฐออกเท่านั้น ระบบจะไม่สร้างหรือปลอมแทน"

**4) คู่มือการใช้งานอ่านง่ายขึ้น**
ปรับ `guide.html`: ขยายขนาดตัวอักษรทั้งหน้า, เพิ่มหัวข้อใหม่ "ยืนยันตัวตนด้วยรหัส OTP", เพิ่มกล่องภาพประกอบ (placeholder) ไว้ 5 จุดสำหรับใส่ภาพหน้าจอจริงในอนาคต, และเพิ่มหัวข้อท้ายเล่มสรุปเอกสารที่สร้างได้/ไม่ได้พร้อมลิงก์อ้างอิงกฎหมาย

> หมายเหตุ: การเปลี่ยนแปลงทั้งหมดใน ver13 อยู่ในเวอร์ชัน SQLite (`node:sqlite`) นี้เท่านั้น ยังไม่ได้ย้ายไปยังเวอร์ชัน PostgreSQL


## ใหม่ใน ver12 (แก้บั๊กฟอนต์หัวตารางที่ซ่อนอยู่)

เจอสาเหตุจริงของ "ฟ้อนไม่ตรงกัน" ที่หัวตารางเอกสาร: class `.num` (ไว้จัดชิดขวาให้คอลัมน์ตัวเลข) ถูกใส่ font-family เป็น JetBrains Mono ไว้ในตัว — ใช้ได้ถูกต้องกับ `<td>` ที่เป็นตัวเลขจริง แต่ดันถูกเอาไปใส่ซ้ำกับ `<th>` หัวตารางที่เป็นข้อความไทยด้วย (เช่น "ฐานภาษี", "หัก ณ ที่จ่าย", "สุทธิ") เพราะแค่ต้องการให้ชิดขวาตรงกับคอลัมน์ตัวเลขด้านล่าง — ผลคือหัวตาราง 3 ใน 5 ช่องใช้ฟอนต์ mono ที่ไม่มีตัวอักษรไทย เบราว์เซอร์เลยสลับไปใช้ฟอนต์ระบบสำรอง ทำให้หัวตารางแถวเดียวกันมีฟอนต์ปนกัน 2 ชุด

แก้โดยแยกหน้าที่ของ class: `.num` เหลือแค่จัดชิดขวา, เพิ่ม `td.num` ให้ใช้ฟอนต์ mono เฉพาะตัวเลขจริง และ `th.num` ให้ใช้ฟอนต์เนื้อหาไทยตามปกติ (ยังชิดขวาเหมือนเดิม) — ครอบคลุมทุกตารางในระบบทั้งหน้า HTML คงที่และตารางที่ render จาก JavaScript


## ใหม่ใน ver11 (แก้ปัญหาฟอนต์ไทย)

พบสาเหตุ 3 อย่างที่ทำให้ตัวอักษรไทย "ห่างๆ ไม่ตรงกัน" และดูไม่เป็นระบบ:

1. **ฟอนต์หลุด**: `.eyebrow` (ป้ายเล็กเหนือหัวข้อ) และ `.contact-item small` ถูกตั้งให้ใช้ฟอนต์ตัวเลข JetBrains Mono ซึ่ง**ไม่มีตัวอักษรไทย** แต่ดันครอบข้อความไทยอยู่ — เบราว์เซอร์เลยเงียบๆ สลับไปใช้ฟอนต์ระบบสำรอง ทำให้หน้าตาไม่เข้าชุดกับข้อความรอบข้าง แก้โดยเปลี่ยนกลับมาใช้ฟอนต์เนื้อหาไทยตามปกติ
2. **letter-spacing ผิดที่**: มีการใส่ letter-spacing (เทคนิคจัดตัวพิมพ์ใหญ่แบบอังกฤษ) ไว้กับป้าย/หัวข้อภาษาไทยหลายจุด (h1-h4, ป้ายหมวดหมู่, stepper, การ์ดสรุป ฯลฯ) ทำให้สระและวรรณยุกต์ไทยดูแยกห่างจากพยัญชนะ — ลบออกทั้งหมด คงไว้เฉพาะจุดที่เป็นตัวเลข/อังกฤษล้วน
3. **ตัวอักษรเล็กเกิน**: หลายจุดใช้ 10-11px ซึ่งเล็กเกินสำหรับอ่านสบาย ปรับขึ้นเป็น 12-13px ทั่วทั้งระบบ (stepper, หัวตาราง, ป้ายสถานะ, การ์ดสรุปแดชบอร์ด, คำอธิบายใต้ช่องกรอก ฯลฯ)

เพิ่มเติม: แก้ CSS class `.stat-card` ที่ชนกันระหว่างหน้าภาพรวมเดิมกับการ์ดสรุปภาษีใหม่ (ver10) โดยแยกเป็น `.dstat-card` ให้ไม่ทับซ้อนกันอีก

## ฟีเจอร์หลัก

**ระบบบัญชีผู้ใช้** — สมัคร/เข้าสู่ระบบ แยกบทบาท creator / agency, รหัสผ่าน scrypt, session HMAC

**เอกสารภาษี** — ใบกำกับภาษี (e-Tax), หนังสือรับรองหัก ณ ที่จ่าย (e-Withholding), บันทึก 50 ทวิฝั่งครีเอเตอร์ พร้อมคำนวณภาษีอัตโนมัติ

**เลขที่เอกสารอัตโนมัติ** — รูปแบบ `TAX-2026-00001`, `WHT-2026-00001` รันแยกตามผู้ใช้และประเภท

**ตรวจสอบข้อมูลก่อนบันทึก** — แจ้งเตือนรายการที่ขาด (ชื่อคู่ค้า ยอดเงิน รายการสินค้า) ทั้งฝั่งหน้าเว็บและ API

**สถานะเอกสาร (workflow)** — แบบร่าง → รอตรวจสอบ → อนุมัติ / ไม่อนุมัติ → ยกเลิก / เก็บถาวร พร้อมควบคุมการเปลี่ยนสถานะที่ถูกต้อง

**ประวัติเวอร์ชัน** — บันทึกทุกการแก้ไข (ผู้แก้ วันเวลา หมายเหตุ) และดูย้อนหลังได้

**อัปโหลด/แนบไฟล์** — ลากวาง (drag & drop), ดูตัวอย่างก่อนบันทึก, จำแนกประเภท (ใบเสร็จ/ใบกำกับ/50 ทวิ/สลิปโอนเงิน), จำกัด PDF/PNG/JPG/WEBP ไม่เกิน 5 MB

**ลายเซ็นอิเล็กทรอนิกส์** — วาดลายเซ็นบน canvas, บันทึกผู้ลงนาม + วันเวลา แสดงบนเอกสาร PDF

**แชร์ + QR ตรวจสอบ** — สร้างลิงก์สาธารณะ, ส่งอีเมล, ดาวน์โหลด QR Code (สร้างเองแบบ pure JS) สแกนแล้วเปิดหน้า verify แสดงความถูกต้องของเอกสาร

**ค้นหาและกรอง** — เลขที่, ประเภท, สถานะ, ช่วงวันที่, คู่ค้า

**ส่งออก** — PDF (พิมพ์), Excel (.xls), CSV (มี BOM ภาษาไทยไม่เพี้ยน)

**การแจ้งเตือน** — กระดิ่งแจ้งเตือน (อนุมัติ/ตีกลับ/แก้ไข/ส่งตรวจ) พร้อมนับที่ยังไม่อ่าน

**Audit Log** — บันทึกทุกการทำงาน: สร้าง แก้ไข เปลี่ยนสถานะ ลงนาม แชร์ อัปโหลด ดาวน์โหลด ส่งออก ลบ

## การต่อฐานข้อมูลจริง (PostgreSQL) ในอนาคต

ทุกการเข้าถึงข้อมูลผ่าน `lib/store.js` ไฟล์เดียว เมื่อจะย้ายไป PostgreSQL
ให้แทนที่ฟังก์ชัน `insert / all / find / findOne / update / remove` ด้วยการ query
ผ่าน `pg` หรือ Prisma โดยส่วน API และหน้าเว็บไม่ต้องแก้ ตัวอย่าง:

```js
const { Pool } = require('pg');
const pool = new Pool({ connectionString: process.env.DATABASE_URL });

async function insert(table, record) {
  const cols = Object.keys(record);
  const ph = cols.map((_, i) => `$${i + 1}`).join(',');
  const { rows } = await pool.query(
    `INSERT INTO ${table} (${cols.join(',')}) VALUES (${ph}) RETURNING *`,
    Object.values(record)
  );
  return rows[0];
}
```

Schema ที่แนะนำ: ตาราง `users`, `documents`, `contacts` (ดูฟิลด์ได้จาก record ที่ `store.insert` สร้าง)

## หมายเหตุ

- ระบบต้นแบบเพื่อการศึกษา ไม่เชื่อมต่อระบบจริงของกรมสรรพากร / ETDA
- ลายมือชื่อดิจิทัลเป็นการ **จำลอง** — หากต้องการไฟล์ PDF/A-3 + XML จริงตามมาตรฐาน
  มพศ. 3-2560 ให้เพิ่มการสร้างฝั่งเซิร์ฟเวอร์ด้วย `pdfkit`, `node-signpdf` และ XML builder
- อัตราภาษี/ค่าลดหย่อนใน `lib/tax.js` ควรปรับตามกฎหมายล่าสุดของกรมสรรพากร
- ก่อนใช้งานจริง ควรตั้งค่า `SESSION_SECRET` เป็น environment variable
```bash
SESSION_SECRET=your-strong-secret node server.js
```
